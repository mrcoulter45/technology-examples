# ChatGPT Tokens, Retrieval, File Uploads & Conversation Context (One‑Stop Guide)

> A comprehensive, one‑stop reference on how ChatGPT accounts for tokens, how uploads are chunked and retrieved, how past conversation context is handled, where AI vs. “just software” is used in the pipeline, and how to shape prompts for low‑token, high‑relevance answers.

*Last updated: 2025‑09‑19*

---

## 1) Executive Summary (TL;DR)

* **Uploads don’t consume chat tokens.** Tokens are only spent on the text actually sent to the model (your request + selected excerpts) and on the model’s reply.
* ChatGPT **doesn’t feed entire files** into the prompt by default. Files are **chunked** and **indexed**; at answer time, it **retrieves only relevant slices**.
* Retrieval uses a **hybrid approach**: semantic embeddings + keyword/symbol search + code/framework heuristics + a reranker. This keeps context **small** and **focused**.
* **Conversation history counts** when included. The slice of prior messages sent with a request consumes **input tokens**; the assistant’s reply consumes **output tokens**. Omitted/summarized history costs nothing.
* **Memory is separate.** Storing long‑term facts doesn’t use chat tokens; **only** memory text injected into a turn consumes tokens.
* **Embeddings/reranking are separate AI steps** (not the main chat LLM) and don’t use your chat tokens. Only the final LLM call does.
* Give **anchors** (filenames, symbols, UI library, storage constraints) to improve retrieval and reduce tokens.

---

## 2) Key Definitions

* **Token** — Small unit of text. Both **input** (prompt/context) and **output** (assistant reply) consume tokens.
* **Context window** — Max tokens the model can consider at once (input + output combined).
* **Chunk** — Contiguous slice of a file (e.g., a function/class/section) used for indexing and retrieval.
* **Embedding** — Vector representation that captures semantic meaning; used for similarity search.
* **Cross‑encoder / reranker** — A smaller AI model that reads the query + a candidate chunk together to score relevance.
* **Hybrid search** — Combines semantic vectors, keyword/symbol matches (BM25/regex), and code‑aware heuristics.
* **Memory** — Optional long‑term user facts stored outside the chat transcript; only injected memory text in a turn counts toward tokens.

## 3) Mental Model: Data & Token Flow

### 3.1 Token‑usage flow diagram (what does / doesn’t consume chat tokens)

```
[You upload files]
        │
        ├─(No chat tokens used for upload)
        │
        ▼
[Preprocessing / Indexing]
  - Chunk files
  - Build metadata (paths, language, symbols)
  - Compute embeddings            ← AI model, NOT chat tokens
        │
        ▼
[Query‑time Retrieval]
  - Embed your request            ← AI model, NOT chat tokens
  - Hybrid search (vectors + BM25 + code heuristics)
  - Rerank with cross‑encoder     ← AI model, NOT chat tokens
  - Select top‑N chunks
        │
        ▼
[LLM Invocation]
  - Build prompt with: your request + selected chunks + relevant history + (optional) memory snippets
  - Model generates answer        ← Chat tokens (input + output) start here
```

**Rule of thumb:** Chat tokens are consumed **only** when text is actually **sent to** or **generated by** the main LLM.

### 3.2 What counts vs. what doesn’t

**Counts**

* The **current request** text you write
* The **selected file chunks** included in the prompt
* The **slice of conversation history** that’s included
* Any **inserted Memory** snippet used this turn
* The **assistant’s reply**

**Does **not** count**

* Uploading files
* Indexing (chunking, metadata, embeddings)
* Query‑time embedding, retrieval, and reranking
* Omitted history not sent this turn
* Memory facts that are stored but **not injected** into the current prompt

## 4) How Uploads & Retrieval Actually Work

### 4.1 Upload vs. process

* **Upload**: stores files for later retrieval. *No chat tokens spent here.*
* **Process**: only the **selected chunks** inserted into the LLM prompt consume tokens.

### 4.2 Chunking

* Files are split into **logical chunks** (typ. 300–1000 tokens), ideally along function/class/section boundaries.
* Each chunk carries **metadata**: file path, language, defined/used symbols, whether test/docs, last modified time, etc.

### 4.3 Candidate Retrieval (hybrid)

* **Semantic vector search** via embeddings to capture intent/synonyms.
* **Keyword/BM25/regex & symbol search** for exact names, filenames, imports/exports.
* **Code‑aware heuristics**: framework conventions (e.g., Angular component/service patterns), entry points, configuration files.
* **Recency/commit hints (optional)**: prefer recently touched code when relevant.

### 4.4 Reranking & Selection

* A **cross‑encoder** (small AI model) re‑scores candidates by reading them with your query.
* **Structural boosts**: symbol definitions, root modules (e.g., `app.module.ts`), central configs get priority.
* **Diversity constraints**: avoid near‑duplicate chunks from one file; ensure coverage.
* **Follow‑links budget**: if a chosen chunk references an undefined symbol, pull a **small neighbor slice** that defines it.
* **Trim to fit context**: take top‑N chunks needed to answer while staying under the context window.

## 5) Where AI Is Used vs. “Just Software”

**AI‑powered steps**

* Computing **embeddings** for chunks and for your query (semantic matching)
* **Cross‑encoder reranking** (query + chunk relevance scoring)

**Engineering steps**

* **Chunking** files on logical boundaries
* **Metadata** extraction (paths, imports/exports)
* **Sorting/merging/trimming** of ranked candidates to fit the context window

> Net effect: AI helps find the right snippets; software keeps the prompt small and deterministic.

## 6) Conversation History & Memory

* **Conversation history**: Each request includes a **trimmed slice** of prior messages. Whatever is included **does** consume input tokens; anything **omitted or summarized** does not.
* **Memory** (if enabled): Long‑term facts are stored outside the transcript. Storing them doesn’t use chat tokens; **only** the memory text injected in a given turn consumes tokens.
* **Practical control**: Keep long threads tidy; ask for a **summary** to replace verbose history; start a **fresh thread** for new topics.

## 7) Strategy When You Don’t Specify Files (Feature Work Across Many Files)

**Operating mode**: **filter → propose → confirm → refine**

1. **Interpret** the feature (break into sub‑tasks and likely code areas)
2. **Search**: scan for filenames, imports/exports, keywords, symbols; use framework clues
3. **Propose** the smallest set of candidate edits with **minimal diffs**
4. **Confirm** assumptions with you (or proceed if obvious)
5. **Refine** quickly with your feedback (now that files are known)

**Why this saves tokens**: We retrieve only the most relevant chunks rather than stuffing the entire repo into the prompt.

## 9) Large Files: Failure Modes & Mitigations

**What can go wrong**

* **God files (10k+ lines)**: relevant function straddles a chunk boundary (partial context)
* **Vague naming**: feature says “dark,” code uses `night`/`nocturnal`/`themeMode=1`
* **Indirection**: toggle UI is dumb; logic buried in a shared directive/service
* **Generated/minified** artifacts included in search results
* **Cross‑language split**: HTML template vs. TS/JS logic scattered across chunks
* **Sparse comments**: no literal keywords to match; only design tokens

**How you can help retrieval**

* **Anchors**: filenames/paths (`app.component.html`, `theme.service.ts`)
* **Symbols**: `ThemeService`, `themeMode`, `isDark()`, `setDark()`
* **Scope**: “Persist with **localStorage**, not cookies.”
* **Negative hints**: “Don’t touch `settings.component.ts`.”
* **UI framework**: “Angular Material; use `mat-slide-toggle` in toolbar.”
* **Bootstrap**: “Initialize in `AppComponent.ngOnInit()`.”

**If retrieval struggles**

* Ask for a **repo map** (theming files/services, key symbols, entry points)
* Provide a **seed snippet** (e.g., the `ThemeService` signature)
* Request a **second‑pass retrieval** with hard anchors (`mat-toolbar`, `ThemeService`)

## 10) Token Management Playbook

* **Narrow the ask** to a specific UI area + behavior + constraints
* Provide **1–3 anchors** (filenames/symbols/UI comps)
* **State constraints** (storage mechanism, initialization location)
* **Exclude** unrelated areas to reduce spurious retrieval
* **Iterate**: approve a plan/diff before broader edits
* For long threads, ask the assistant to **summarize prior context** and proceed from the summary
* **Start a fresh thread** for unrelated topics to keep history light

## 11) Detailed Accounting & Billing Nuances

* **Embeddings models**: Separate from the main chat LLM. They create semantic vectors for chunks/queries. They **do not consume chat tokens**; usage may be tracked separately.
* **Cross‑encoder/reranker**: Also separate small models used pre‑prompt; **no chat tokens** consumed.
* **Main LLM**: Only when the prompt is built (your text + selected chunks + included history + optional memory) do **chat tokens** start accruing. The **assistant’s reply** also consumes tokens.
* **Conversation history**: Whatever slice is included in the current request **does** count. Older parts may be summarized or omitted to fit the context window; omitted text costs nothing.
* **Uploads & Memory**: Uploading and storing long‑term Memory facts don’t consume chat tokens. Only **retrieved file chunks** and **inserted memory text** included in the current prompt consume tokens.

## 12) FAQ

**Do embedding/reranking steps consume chat tokens?**
No. They are separate preprocessing AI steps. Chat tokens are consumed only by the main LLM call (prompt + selected chunks) and the model’s reply.

**Do past messages count toward tokens?**
Yes. The portion of the chat history included in a request counts as **input tokens**; the assistant’s reply counts as **output tokens**. Omitted/summarized history doesn’t count.

**How are file uploads and Memory different from chat history?**
Uploads are **pre‑indexed/chunked**; only retrieved snippets inserted into a turn consume tokens. **Memory** is stored separately; **only** memory text injected into a turn consumes tokens.

**Can I upload an arbitrarily large file and still pay few tokens?**
In principle yes—only selected chunks enter the prompt. In practice, there are limits: indexing caps, retrieval imperfections, and the model’s context window. Provide anchors to improve reliability.

**Will the entire file ever be loaded?**
Only if you ask for something broad (e.g., “Summarize the entire file”). Otherwise, retrieval injects **just enough** to answer.

**What if the wrong chunk is chosen?**
Provide a hint (filename/symbol) or a small excerpt. Ask for a second‑pass retrieval with your hint as a hard anchor.

**Is this just a sorting algorithm, or is AI used?**
Both. Embeddings and cross‑encoder reranking are AI; chunking/metadata/selection are software.

**What’s the practical benefit of anchors/naming?**
Clear filenames/symbols/framework terms drastically improve retrieval recall/precision and reduce token usage by avoiding noisy context.

## 15) Appendix A — Visuals & Diagrams

### A.1 Retrieval Pipeline (High‑Level)

```
[You upload files]
    └─ index:
       - chunk by logical boundaries
       - attach metadata (path, language, symbols)
       - compute embeddings (semantic vectors)

[You ask a question]
    └─ retrieve candidates:
       - semantic vector search (embeddings)
       - keyword/BM25/code-aware signals (imports, filenames)
       - framework heuristics (e.g., Angular component/service patterns)

    └─ rerank:
       - cross-encoder/model re-scores relevance
       - structural boosts (entry points, symbol definitions)
       - diversity constraint (avoid near-duplicates)

    └─ trim & expand neighbors:
       - select top-N chunks to fit context
       - optionally pull small defining slices for referenced symbols

[LLM call]
    └─ build prompt with your request + selected chunks
    └─ model generates answer
```

### A.2 Token‑usage flow (duplicate here for quick reference)

```
NO CHAT TOKENS →
  • Upload files
  • Indexing: chunking, metadata, embeddings
  • Query-time: embed your request, hybrid retrieve, rerank
  • Saving long-term Memory facts (if enabled)

CHAT TOKENS →
  • Final LLM prompt: your request + selected chunks
  • Conversation history slice included in the request
  • Inserted Memory snippets (if any)
  • Model output: the assistant’s reply
```
